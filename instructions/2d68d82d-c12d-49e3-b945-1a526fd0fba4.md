# fastapi-mcp → fastmcp 이전

## 배경

`mcp` 1.x는 legacy다. 장기적으로 폐기된다.

현재 gateway의 MCP 레이어는 `fastapi-mcp==0.4.0`에 의존하고, 이 패키지는
`mcp>=1.12.0`을 **상한 없이** 선언한다. `mcp 2.0.0`에서
`Server.__init__(name, description)` → `Server(name)`으로 시그니처가 바뀌어,
핀 없이 이미지를 재빌드하면 `app/main.py`의 `FastApiMCP(...)` 생성 시점에
`TypeError`로 기동이 실패한다. (실제 장애 발생 → PR #13에서 `mcp<2.0.0` 핀으로 hotfix)

`fastapi-mcp`는 0.4.0(2025-07-28) 이후 릴리스가 없다. 13개월째 정체이므로
업스트림이 mcp 2.x를 지원할 것이라 기대할 수 없다. 핀을 유지하면 legacy SDK에
고착되고 보안 패치 경로가 없다.

→ 유지보수되는 대체 라이브러리로 이전하고 PR #13의 `mcp<2.0.0` 핀을 제거한다.

## 목표 / 비목표

**목표**

- `mcp` 2.x 계열 위에서 동작
- 노출 tool 7개의 **이름·인자·동작 불변** (기존 MCP 클라이언트 설정 호환)
- `mcp<2.0.0` 핀 제거

**비목표**

- MCP tool 추가·삭제·이름 변경. 이번 작업은 순수 이전이다.
- REST 라우트·`verify_admin_token`·audit·`models.py`·`wikijs_client.py` 로직 변경
- `/pages/download`, `/health`를 tool로 노출 (계속 제외)

## 현재 구조 — 교체 표면

fastapi-mcp는 얇은 반영(reflection) 레이어다. 비즈니스 로직은 FastAPI 라우트에
있고 이관 대상이 아니다. 실제로 묶여 있는 곳은 두 군데뿐이다.

**1. `app/main.py:438-444` — 7줄**

```python
mcp = FastApiMCP(
    app,
    name="wikijs-agent-gateway",
    exclude_operations=["health", "download_page"],
    headers=["authorization"],
)
mcp.mount_http()
```

이 7줄이 하는 일:

| 역할 | 현재 수단 |
|---|---|
| 라우트 → tool 자동 생성 | `FastApiMCP(app)` + 각 라우트의 `operation_id` |
| tool 제외 | `exclude_operations=["health", "download_page"]` |
| **Authorization 헤더 forward** | `headers=["authorization"]` |
| HTTP transport 마운트 | `mount_http()` (`/mcp`) |

**2. `tests/test_mcp_server.py` — 182줄, 전면 재작성**

견적의 대부분이 여기다. 이 테스트는 fastapi-mcp **private API**에 직접 붙어 있다.

- `mcp._execute_api_tool(...)` (`:73`)
- `mcp._http_client`, `mcp.operation_map`, `mcp.tools`
- `from fastapi_mcp.types import HTTPRequestInfo` (`:13`)

라이브러리를 갈면 이 harness는 전부 무효다. 신규 harness 설계가 필요하다.

## 핵심 리스크 — auth 헤더 forward

가장 중요한 제약이다.

현재 `headers=["authorization"]` 한 줄로, MCP 요청의 Bearer 토큰이 내부 ASGI
호출을 타고 라우트 의존성까지 전달된다. 덕분에 MCP 레이어에 **별도 auth 코드가
없고**, `verify_admin_token`과 audit 기록이 REST와 완전히 동일한 경로로 재사용된다.

대체 라이브러리가 같은 방식을 제공하지 못하면 MCP 전용 auth 경로를 따로 써야
하고, 그 순간 이 작업은 "얇은 교체"가 아니라 인증 로직 이중화가 된다. 견적이
배로 뛰고 보안 검토 대상이 된다.

→ 그래서 Phase 0에 go/no-go 게이트를 둔다.

## 후보

**`fastmcp` (PrefectHQ, 현재 v3.2.x, 활발히 유지보수)** — fastapi-mcp와 같은
"기존 FastAPI 앱을 반영" 모델을 제공한다. 채택 시 `main.py`는 계속 10~15줄 수준.

**대안(비권장): 공식 `mcp` SDK에 직접 작성** — tool 7개의 스키마를 손으로 선언.
`models.py`의 pydantic 모델을 중복시키고 `main.py`가 150~250줄 늘어난다.
Phase 0에서 fastmcp가 탈락할 때만 검토한다.

> **주의**: 아래 Phase 0 항목은 **미검증**이다. 이 지시서를 쓰는 시점에 fastmcp
> 문서 확인을 완료하지 못했다. API 표면을 추측으로 확정하지 말고 반드시 문서로
> 검증한 뒤 Phase 1로 넘어간다.

## 작업 단계

### Phase 0 — 타당성 검증 (go/no-go 게이트)

문서로 확인한다. 코드를 쓰기 전에 끝낸다.

- [x] fastmcp가 기존 FastAPI 앱에서 tool을 생성하는 API 확인 (`from_fastapi` 계열)
- [x] **Authorization 헤더를 하위 라우트 의존성까지 forward하는 수단 확인** ← 최우선
- [x] 특정 라우트를 tool에서 제외하는 수단 확인 (`health`, `download_page`)
- [x] 생성되는 tool 이름을 `operation_id`에 고정할 수 있는지 확인
      (이름이 바뀌면 기존 MCP 클라이언트가 깨진다)
- [ ] 기존 FastAPI 앱에 HTTP transport를 `/mcp` 경로로 마운트하는 방법 확인
- [ ] fastmcp가 요구하는 `mcp`·`fastapi`·`pydantic` 버전이 현재 핀과 충돌하지 않는지 확인

**게이트**: auth forward가 불가하면 중단하고 재설계한다. `mcp<2.0.0` 핀을
유지한 채 지시서에 결론을 기록하고 별도 판단을 받는다.

### Phase 0 결과 (2026-08-17) — 조건부 GO

문서 확인 출처: fastmcp 공식 문서 (`docs/integrations/fastapi.mdx`,
`docs/servers/middleware.mdx`, `docs/servers/dependency-injection.mdx`).

**확인된 것**

| 항목 | 결과 | 수단 |
|---|---|---|
| FastAPI 앱 → tool 생성 | ✅ | `FastMCP.from_fastapi(app, ...)` |
| tool 이름 고정 | ✅ | `operation_id`가 곧 component 이름. `mcp_names={operationId: name}`으로 명시 매핑도 가능 |
| 라우트 제외 | ✅ (방식 변경) | `RouteMap(pattern=..., mcp_type=MCPType.EXCLUDE)` |
| 기본 매핑 | ✅ | 기본이 "모든 endpoint → Tool"이라 현재 구성(7 tool)과 일치 |

**제외 방식이 바뀐다**: fastapi-mcp는 `exclude_operations=["health", "download_page"]`로
**operation_id** 기준이었으나, fastmcp `RouteMap`은 **method / path pattern / tag**
기준이다. 따라서 path pattern으로 바꿔 써야 한다.

```python
route_maps=[
    RouteMap(pattern=r"^/health$", mcp_type=MCPType.EXCLUDE),
    RouteMap(pattern=r"^/pages/download$", mcp_type=MCPType.EXCLUDE),
]
```

라우트 경로가 바뀌면 제외가 조용히 풀리므로, 제외 대상 2개가 tool 목록에
없다는 것을 테스트로 고정한다 (Phase 2에 이미 항목 있음).

**미해결 — auth forward가 문서상 등가물이 없다** ← 이번 Phase 0의 핵심 결과

문서화된 유일한 인증 패턴은 **정적 토큰**을 클라이언트에 박는 것이다.

```python
# fastmcp 문서의 방식 — 우리에게는 쓸 수 없다
mcp = FastMCP.from_fastapi(
    app=app,
    httpx_client_kwargs={"headers": {"Authorization": "Bearer secret-token"}},
)
```

이걸 그대로 채택하면 gateway가 admin 토큰을 서버측에 내장하게 되고,
**MCP로 접속한 모든 호출자가 쓰기 권한을 얻는다.** 현재
`headers=["authorization"]`의 per-request forward와 보안 등급이 다르다.
수용 기준 4·5·6 위반이며 채택 불가.

**조합 가능성은 있다 (미검증)**: fastmcp는 들어온 요청 헤더를 per-request로
읽는 `get_http_headers()` / `CurrentHeaders()`를 제공한다(contextvar 기반,
HTTP 요청이 없으면 빈 dict). 이를 outgoing httpx 요청 훅에서 꺼내 실어보내는
조합이 성립할 수 있다.

```python
# 가설 — 반드시 spike로 증명해야 한다
from fastmcp.server.dependencies import get_http_headers

async def _forward_auth(request: httpx.Request) -> None:
    if auth := (get_http_headers() or {}).get("authorization"):
        request.headers["authorization"] = auth

mcp = FastMCP.from_fastapi(
    app=app,
    httpx_client_kwargs={"event_hooks": {"request": [_forward_auth]}},
)
```

이 조합은 **문서에 없다.** tool 호출의 contextvar가 httpx 요청 훅까지
전파되는지에 의존하므로, 추측으로 확정하지 말고 spike로 증명한다.

### Phase 0.5 — auth forward spike (게이트 확정)

Phase 1로 넘어가기 전에 이것만 먼저 증명한다. 실패하면 Phase 1을 시작하지 않는다.

- [ ] `.venv`에 fastmcp 설치 (`uv pip`, 전역 규칙)
- [ ] `from_fastapi`가 앱을 호출하는 transport 확인 —
      ASGITransport(in-process)인지 실제 네트워크인지. 후자면 배포 구성이 바뀐다
- [ ] **증명 1 (positive)**: 유효한 `GATEWAY_ADMIN_TOKEN`을 MCP 요청 헤더로 실어
      `upsert_page` 호출 → 라우트의 `verify_admin_token` 통과 + audit 기록
- [ ] **증명 2 (negative, 더 중요)**: 토큰 없이 / 틀린 토큰으로 `upsert_page` 호출
      → 거부. 정적 토큰이 새어 무조건 통과하는 일이 없음을 확인
- [ ] 읽기 tool은 토큰 없이 통과

**증명 2가 핵심이다.** positive만 통과하면 "정적 토큰이 박혀서 다 통과하는"
상태와 구분되지 않는다. 인증 경로이므로 반드시 실패 케이스로 검증한다.

**게이트 결과별 조치**

| 결과 | 조치 |
|---|---|
| 둘 다 통과 | Phase 1 진행 |
| forward 불가 | **중단.** `mcp<2.0.0` 핀 유지, 지시서에 기록하고 판단 요청. 정적 토큰 방식으로 우회하지 않는다 (권한 상승) |

### Phase 1 — 구현

- [ ] `requirements.txt`: `fastapi-mcp` 제거, `fastmcp` 추가, `mcp<2.0.0` 핀 제거
- [ ] `fastmcp`도 상한 없는 transitive 의존을 갖는지 확인하고, 재현성 확보 수단을
      정한다 (핀 정책 결정 — hotfix에서 학습한 교훈)
- [ ] `app/main.py` MCP 블록 교체 (`from fastapi_mcp import FastApiMCP` 포함)
- [ ] tool 7개 이름이 이전과 **정확히 동일**한지 확인

### Phase 2 — 테스트 재작성

- [ ] `tests/test_mcp_server.py` 신규 harness 작성.
      가능하면 private API 대신 공개 클라이언트 API로 호출한다 —
      기존 테스트가 private API에 붙어 있던 것이 이번 재작성 비용의 원인이다.
- [ ] 기존 5개 케이스 동등 커버리지 유지:
      tool 노출 목록 / 읽기 tool 무인증 동작 / 쓰기 tool 토큰 없음 거부 /
      쓰기 tool 잘못된 토큰 거부 / 쓰기 tool 정상 토큰 성공 + audit 기록
- [ ] `health`·`download_page`가 tool에 없음을 검증

### Phase 3 — 문서·검증

- [ ] `CLAUDE.md` MCP 서버 섹션 갱신 (fastapi-mcp 언급 제거)
- [ ] `README.md` 갱신
- [ ] `output/wikijs-gateway-skill.md` + `_ko.md` 동시 갱신 (tool 이름 변동 없으면 생략 가능)
- [ ] 전체 테스트 통과
- [ ] **실제 MCP 클라이언트로 스모크** — 단위 테스트만으로는 transport 회귀를
      잡지 못한다. tool 7개 목록·읽기 호출·쓰기 인증·audit 파일 생성 확인
- [ ] 컨테이너 재빌드 후 기동 확인 (배포 담당자 실행)

## 수용 기준

1. `mcp` 2.x로 설치되고 컨테이너가 정상 기동한다
2. tool 7개 이름이 이전과 동일: `get_page_by_path`, `get_page_by_uuid`,
   `search_pages`, `get_pages_by_paths`, `dry_run_patch`, `patch_section`, `upsert_page`
3. `health`, `download_page`는 tool로 노출되지 않는다
4. 읽기 tool은 토큰 없이 동작한다
5. 쓰기 tool은 `GATEWAY_ADMIN_TOKEN`을 강제하고 audit log를 남긴다
6. MCP 레이어에 REST와 별개인 auth 로직이 존재하지 않는다
7. `requirements.txt`에 `mcp<2.0.0` 핀이 없다

## 롤백

`app/main.py` MCP 블록 + `requirements.txt` + `tests/test_mcp_server.py`만
되돌리면 원복된다. REST 라우트·인증·audit·DB·Git storage에 영향 없다.
운영 롤백은 이전 이미지 태그로 재기동.

## 결정 사항

- hotfix(PR #13)와 분리한다. 이전 작업은 auth forward 경로를 건드리고 실제 MCP
  클라이언트 검증이 필요해 리스크 성격이 다르다.
- tool 이름은 바꾸지 않는다. 이름 변경은 이전 작업이 아니라 breaking change다.
- 기능 이득은 0이다. 이 작업의 유일한 목적은 legacy SDK 탈출이므로,
  범위를 넓히지 않는다. Phase 0에서 막히면 넓히기보다 멈춘다.
