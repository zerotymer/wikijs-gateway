# fix: /pages/by-uuid type 파라미터 누락 시 PAGE_NOT_FOUND 버그

## 배경

`GET /pages/by-uuid?uuid=<UUID>` 호출 시 `type` 파라미터를 생략하면 실제
페이지가 존재함에도 `PAGE_NOT_FOUND`를 반환하는 버그가 발견됐다.

- 실패: `GET /pages/by-uuid?uuid=55723065-ac44-4a21-828e-aca40d0011c5`
- 성공: `GET /pages/by-uuid?uuid=55723065-ac44-4a21-828e-aca40d0011c5&type=skill`

원인: `wikijs_client.py`가 경로를 `{uuid}` 단독으로 조립하는데,
실제 페이지 경로는 `{type}/{uuid}` 형태여서 `type` 생략 시 조회 불가.

GitHub Issue: [#5](https://github.com/zerotymer/wikijs-gateway/issues/5)

## 목표

`type` 파라미터 없이 UUID만으로도 페이지를 찾을 수 있도록 한다.

## 구현 방향

`app/wikijs_client.py`의 `get_page_by_uuid` 함수에서 `type` 생략 시
다음 fallback 전략 중 하나를 적용한다.

### 방법 A — GraphQL `path` prefix 와일드카드 조회 (권장)

`type`이 없으면 path 조건 없이 UUID 문자열을 포함하는 페이지를 GraphQL로
조회한다. Wiki.js `pages.list` 또는 `pages.search`를 활용해
`path` 값이 UUID로 끝나는 결과를 필터링한다.

### 방법 B — 순차적 prefix 시도

공통 prefix 목록(`skill`, `guide`, `agent`, `doc`, `ref` 등)을
순서대로 시도해 첫 번째 hit을 반환한다. prefix 목록은 설정값으로 관리한다.

### 방법 C — `pages.singleByPath` 두 번 조회 생략, UUID 직접 매핑

Wiki.js GraphQL에 UUID 기반 직접 조회 API가 있으면 활용한다.
없으면 방법 A를 우선 적용한다.

## 구현 단계

1. `app/wikijs_client.py` — `get_page_by_uuid` 함수 수정
   - `type` 있으면 현행 유지: `path = f"{type}/{uuid}"`
   - `type` 없으면 fallback 조회 적용 (방법 A 우선)
2. `app/main.py` — `/pages/by-uuid` 라우터: 변경 없음 (클라이언트 내부에서 처리)
3. `tests/test_routes_by_uuid.py` — 테스트 케이스 추가
   - `type` 없이 UUID만으로 조회 성공
   - `type` 있는 기존 케이스 회귀 확인
   - UUID 없는 경우 여전히 `PAGE_NOT_FOUND` 반환 확인

## 완료 기준

- `GET /pages/by-uuid?uuid=<UUID>` (`type` 생략) → 페이지 정상 반환
- `GET /pages/by-uuid?uuid=<UUID>&type=<type>` → 기존 동작 유지
- 새 테스트 모두 통과
- 기존 테스트 회귀 없음
