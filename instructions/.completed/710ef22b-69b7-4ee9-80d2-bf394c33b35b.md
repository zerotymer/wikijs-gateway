# Step 9: MCP 서버 기능 추가

## 배경

현재 게이트웨이는 순수 HTTP REST API(FastAPI)다. `output/api-spec.html`과
아키텍처 문서에서 "MCP 서버"는 **게이트웨이를 호출하는 클라이언트**로만
언급될 뿐, 게이트웨이 자체는 MCP 프로토콜(JSON-RPC over stdio/HTTP)을
제공하지 않는다.

목표: MCP 클라이언트(Claude Desktop, Claude Code, 기타 agent)가 별도 HTTP
래퍼 없이 게이트웨이에 직접 붙어 Wiki.js 문서를 읽고(선택적으로 쓰고)
검색할 수 있게 한다.

## 목표 (Scope)

기존 8개 REST 엔드포인트를 **재구현하지 않고 재사용**해 MCP tool로 노출한다.
REST API는 그대로 유지한다(MCP는 추가 표면, 대체 아님).

노출할 MCP tool (기존 핸들러/`wikijs_client` 재사용):

| MCP tool | 매핑 | 인증 등급 |
|---|---|---|
| `get_page_by_path` | `GET /pages/by-path` | read |
| `get_page_by_uuid` | `GET /pages/by-uuid` | read |
| `search_pages` | `GET /pages/search` | read |
| `get_pages_by_paths` | `POST /pages/by-paths` | read |
| `dry_run_patch` | `POST /pages/dry-run` | admin |
| `patch_section` | `POST /pages/patch-section` | admin |
| `upsert_page` | `POST /pages/upsert` | admin |

`/health`는 tool 대신 MCP 리소스나 생략 가능(우선순위 낮음).

## 결정 사항 (2026-06-28, 사용자 확정)

> 이 절은 지시서 초안 작성 시점의 가정을 현재 코드/사용자 결정에 맞게 정정한 것.

1. **전송: HTTP 서버** (stdio 아님). MCP를 별도 stdio 진입점이 아니라 기존
   FastAPI 앱에 `mount_http()`로 mount → 같은 uvicorn(`127.0.0.1:8088`)에서 제공.
2. **인증: 게이트웨이와 동일한 Bearer 토큰**. HTTP라 `Authorization` 헤더가
   살아 있으므로, 기존 라우트별 의존성(`verify_admin_token`)을 그대로 재사용한다.
   read는 무인증, admin은 `GATEWAY_ADMIN_TOKEN` — REST와 100% 동일.
3. **삭제된 가드 요구 제거**: `GATEWAY_MODE`/`ALLOW_PATH_PREFIXES`는 커밋
   `dd051db`("gateway 레벨 인증 및 모드 시스템 전면 제거")에서 이미 제거됐고
   현재 코드에 없다. 따라서 `MODE_NOT_ALLOWED`/`PATH_NOT_ALLOWED` 관련 요구·
   테스트는 폐기한다(존재하지 않는 기능).

## 접근 방식 (lazy — 채택: fastapi-mcp 자동 노출)

> ctx7로 확인 완료(`/tadata-org/fastapi_mcp`, 0.4.0). 아래는 검증된 방향.

**채택 — `fastapi-mcp`로 기존 FastAPI 앱 자동 노출 (최소 코드)**
- 기존 8개 라우트를 reflection으로 MCP tool로 변환해 같은 앱에 mount.
- tool 스키마는 기존 pydantic 모델에서 자동 생성. 핸들러 재작성 0줄.
- **인증 재사용 핵심**: `FastApiMCP(app, headers=["authorization"])`로
  Authorization 헤더를 tool 호출에 forward → write 라우트의 `verify_admin_token`
  Depends가 그대로 실행된다. read 라우트는 의존성이 없어 무인증 유지.
  → 새 auth 코드 0줄, REST와 동일 모델.
- 전역 `AuthConfig(dependencies=...)`는 **쓰지 않는다**(read까지 막아버림).
  라우트별 기존 의존성에 맡긴다.

> `fastmcp` 수동 정의(2순위)는 불필요 — HTTP 전송이라 헤더 기반 auth가
> 자동 반영되므로 자동 노출로 충분.
> 새 의존성은 **개인 인덱스(private index) 경유 설치**(전역 규칙). PyPI 임의 설치 금지.

## 인증·안전 (필수 — 단순화 금지)

- read tool: 인증 없음(기존 read 라우트 의존성 그대로).
- admin tool(`dry_run_patch`, `patch_section`, `upsert_page`): 기존
  `verify_admin_token`이 forward된 Authorization 헤더로 실행 → 토큰 없거나
  틀리면 401/403. 토큰은 MCP 클라이언트가 Bearer 헤더로 전달.
- 모든 write/dry-run tool 호출은 기존 핸들러를 그대로 거치므로 **audit log**가
  자동으로 남는다(중복 구현 없음).
- 게이트웨이 핵심 제약 유지: PostgreSQL 직접 접근 금지, Git 직접 쓰기 금지,
  Docker socket mount 금지.

## 작업 항목

1. `fastapi-mcp==0.4.0`을 개인 인덱스 경유로 `requirements.txt`에 고정 추가.
2. `app/main.py`에 `FastApiMCP(app, headers=["authorization"])` + `mount_http()`
   추가(앱 생성 직후, 라우트 등록 후). 엔드포인트별 `operation_id` 정리해
   tool 이름을 안정화(`get_page_by_path` 등).
3. README/`output/api-spec.html`·SKILL 파일(영/한)에 MCP 사용법 섹션 추가
   (HTTP 엔드포인트 `/mcp`, Bearer 헤더 전달 예시 JSON 1개).
4. 테스트 작성(아래).

## 테스트 규칙 (전역: 테스트 없는 기능 PR 금지)

- `tests/test_mcp_server.py`:
  - `/mcp` mount가 살아 있고 tool 목록에 7개 tool이 노출되는지.
  - read tool이 mock된 `wikijs_client`로 올바른 페이로드를 반환하는지.
  - admin tool이 토큰 없이/잘못된 토큰으로 호출 시 401/403으로 거부되는지.
  - admin tool이 올바른 Bearer 토큰으로 호출 시 정상 동작하는지.
  - write/dry-run tool 호출이 audit log를 남기는지(기존 핸들러 경유 확인).
- Wiki.js 호출은 `respx` mock 사용(기존 통합 테스트 패턴 준수).
